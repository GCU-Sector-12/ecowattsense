# Measuring the real energy of a PC on Windows: findings of 11 November 2026

This file is the full record of what was established on 11 November 2026. It is not a summary. It joins four kinds of work: a literature and source review (67 sources in the main report, more in four research notes), raw probes on one laptop, a battery night measured with Windows tools, and a first guided calibration run with a small test program.

## How to read the labels

Every fact is marked with one of two labels.

* **tested here**: measured on the HP 250 G7 test laptop on 11 November 2026, with a probe, a Windows tool or the calibration program.
* **read only**: taken from a source (documentation, code, paper, forum, pull request). We did not run it. The source is in section 10.

Other tags used in the text:

* **own calculation**: simple arithmetic done by the author of this record on the figures shown.
* **single source**: one author or one small project says it; nobody confirmed it.
* **search summary only**: the research tool saw only a search-engine summary of the page, not the page.
* **proposal**: a suggestion. Decisions belong to the project owner and the team.

Paths are written without user folders. Device ids, serial numbers and the computer name are left out on purpose.

## 1. Purpose and test machine

### 1.1 Purpose

EcoWattSense needs the real energy a PC uses. The server has a table of watts per state (`energy_rates`). The question of the day was: what can a normal program on Windows read that is real, with no administrator rights and no foreign driver? The work covered:

1. every known path to a power or energy reading on Windows 10 and 11, with rights, drivers and accuracy;
2. what the test laptop really shows on each path;
3. how far a real battery night is from the `energy_rates` table;
4. a first guided calibration run (about 18 minutes, seven states) that builds a power model of one laptop.

### 2.2 What the table says in short

* A normal program with no administrator rights and no own driver can read only **two** real things today: the **CPU package energy on Windows 11** (likely, not confirmed) and the **battery charge of a laptop on Windows 10 and 11** (confirmed on our laptop).
* **Nothing** a normal program can read is the energy at the wall socket. The battery sees the DC side only, and only while on battery. The CPU package is a part of the total.
* Every other path needs administrator rights, a maker-supplied package, a foreign driver or a vendor tool.

## 4. Laptop makers: what they ship

### 4.1 HP

* **DTT/DPTF.** HP ships the Intel Dynamic Tuning driver in softpaqs (for example sp102094 and others). The HP 250 G7 has it (**tested here**). HP also ships the PMT driver for newer platforms (sp151256 for an Envy 17, Windows 11 23H2, PMT 3.1.2.2; a "Core Series 3" package sp173087), **read only**.
* **Own WMI.** Classes `HP_BIOSNumericSensor`, `HPBIOS_BIOSNumericSensor` and state-sensor classes exist on the HP 250 G7 in `root\wmi`/`root\HP`, but the sensor query returned empty rows (**tested here**). The Linux `hp-wmi-sensors` documentation says only temperature, fan and chassis-intrusion sensors were seen on real machines; a "Watts" unit exists in the schema but nothing publishes it (**read only**).
* **Tools.** HP Performance Advisor and Sure Admin were not researched for power data.
* **What HP gives.** Heat and fans, no watts.

### 4.2 Lenovo

* **DTT/DPTF.** Lenovo ships the same Intel DTT driver on many Intel models: ThinkPad E14 and E15 (driver 8.7.10700.22502 for Windows 10 and 11), V50s, IdeaPad, Yoga, Legion. A Lenovo security advisory (LEN-140527) lists DTT versions (**read only**, from the task brief; no link kept). **Not tested on a Lenovo.**
* **Own WMI.** The Linux `lenovo-wmi-other` driver documents power limits (`ppt_pl1_spl`, `ppt_pl2_sppt`, `ppt_pl3_fppt`) as settings, not as measurements. The community Legion Toolkit sets PL1 and PL2. Lenovo Vantage and ThinkPad WMI: no source found on any power reading (**read only**).
* **What Lenovo gives.** The same DTT class as HP, if the driver is present. Whether `EsifDeviceInformation` there needs administrator rights, and whether participant 3 and 4 mean the same, is unknown. The report lists a Lenovo run as a next test.

### 4.3 Dell

* **Dell Command | Monitor.** WMI namespace `root/dcim/sysman`. `DCIM_NumericSensor` covers voltage, current, temperature and fans; `DCIM_Battery` gives battery inventory. No watts were found. Administrator rights on the client are a listed prerequisite. The FAQ page we read is stale (it names version 9.0; 10.x guides exist). Dell sensor-profile documents define power sensors for servers, which is not proof for client PCs (**read only**).

### 4.4 Others

* **Microsoft Surface Book 1 and Surface 3** carry real hardware power meters (Maxim chips) that EMI exposes on Windows 10 (read only: Mozilla slides). Many other devices declare a meter in their ACPI tables without the chip fitted, which gives zero or empty counters, as the "Power Meter" counters on our HP (value 0, **tested here**).
* **ASUS** boards: older DTT builds for Windows 10 exist on third-party driver sites (for example a ProArt B760 package; search summary only).
* The Intel Community says the DPTF driver is supplied by the PC maker (search summary only).

### 4.5 What the makers give, in one line

HP, Lenovo and the DTT-based makers share one Intel stack that shows a package-like power to administrators. The makers' own WMI layers give temperatures, fans, limits and battery data, not measured power.

## 5. Everything measured on the HP 250 G7

All numbers in this section are **tested here**, on 11 November 2026, unless a line says otherwise.

### 5.1 Probe 1 (normal user, charger connected, about 13:50)

* Not administrator. Windows 10 Pro 22H2, build 19045. Intel Core i5-8265U.

### 5.5 Intel DTT `EsifDeviceInformation` (administrator only)

* Class `root\wmi` `EsifDeviceInformation`: **Access denied** for a normal user (tested here). The error code was not recorded (0x80070005 or 0x80041003 would show the mechanism).
* As administrator: six instances (participants 0 to 5) with fields `Power`, `Temperature`, `Active`. The `Power` field is in **tenths of a watt**. Participants 0, 1, 2 and 5 stayed at 0 W; participants 3 and 4 carried power. Participants 0, 1, 2 showed their own temperatures (1, 38 to 40 and 0 C); participants 3, 4, 5 shared one temperature reading.
* **Rest, then 8-thread load, then rest** (read every 2 s):

| Phase | Participant 3 (package-like) | Participant 4 (cores-like) | Temperature |
|---|---|---|---|
| Rest | 1.1 to 4.7 W | 0.4 to 3.5 W | 45 to 54 C |
| Load, 8 busy threads | 15.1 W at the start, then 23.1 to 26.9 W | 13.8 W at the start, then 21.9 to 25.5 W | 67 to 77 C |
| Rest again | 0.9 to 2.5 W (one reading of 21 W right after the load) | 0.2 to 1.3 W | 57 to 63 C |

* Reading: participant 3 behaves like the CPU package, participant 4 like the cores. **The unit and meaning are derived from this test; Intel does not document the class.** The values are instant and jump, so a reader would need to poll every 1 to 2 seconds.
* In the calibration run (section 5.7) the mean package power at 100 % CPU was only **14.9 W**, close to the nominal 15 W of this processor class (general knowledge, not from the files). The 23 to 27 W of the short test was a burst above that limit.

### 5.6 EnergyReader (small C# console program, administrator)

Logged the DTT package power and the battery charge side by side. At rest on battery the laptop used **3.7 to 4.1 W** and the package **1.9 W** (about 46 to 51 %, own calculation). An earlier hand log (`energy-log.csv`, 16:03 to 16:17, 14 minutes, load and brightness unknown) showed a mean package power of 2.3 W and battery power of about 5.1 W (1,197 mWh in 851 s), so the package was **about 46 %** of it (own calculation; from the main report). In that log `RemainingCapacity` changed by 22 to 228 mWh at intervals from a few seconds up to 2 minutes, and stayed at 35,864 mWh for 19 minutes on the charger. The task draft talks about steps of about 2,177 mWh (6 %); those steps belong to `powercfg /batteryreport` and its hourly sampling. The 22 to 228 mWh spread in the hand log was not explained.

* DTT package temperature: 41 to 44 C at rest, 73 to 74 C under CPU load, 52 C in the graphics phase. The thermal zone maximum was 29.85 C in all phases, so that source was not informative.

* Source "Energy Meter counters": missing in 462 of 462 samples (no instance).

| Quantity | Value | Note |
|---|---|---|
| Screen | 0.0211 W per 1 % brightness | (6.62 - 4.52) / 100 |

* From 0 % to 50 % brightness the laptop gained 0.34 W, from 50 % to 100 % it gained 1.77 W. The first step (11 mWh) is one battery step, so it is within the noise.
* The lowest brightness still lights the screen (expected): phase 1 is not a "screen off" reference.
* The package is 24 to 36 % of laptop power at rest and 61 to 67 % under CPU load. This agrees with the 46 % of the hand log and sits in the range found in the literature (section 6.2).

Not yet tested on hardware: the latest version of the program (real display-state reading with `GUID_CONSOLE_DISPLAY_STATE`, and a more reliable display-off command), see section 9.

### 5.8 Comparison with `energy_rates`

The server's table: laptop **Active 15 W, Idle 9 W, Unused 3 W**; desktop 55, 40, 25 W. `energy_uj` is 0 on battery (wall-socket meaning, correct by contract). The contract fields `battery_energy_uj` and `device_energy_uj` exist and the server stores them, but the Windows client does not send them. `cpu_percent` has no effect on energy.

## 6. Accuracy from the literature (read only)

### 6.1 RAPL by generation

| Generation | What the studies found |
|---|---|
| Sandy Bridge and Ivy Bridge (2011 to 2012) | RAPL is a model built from event counts. Workload dependent. On a 2-socket Sandy Bridge-EP the package plus DRAM sat about 50 W below the AC input, steady across workloads |
| Haswell and later (2013 to 2014) | RAPL became a measurement through integrated voltage regulators. On a 2-socket Haswell-EP the correlation to AC was almost perfect and the residual below 3 W (reference LMG450, 0.07 % + 0.23 W). RAPL cannot show fans, PSU losses and boards |
| Haswell and Sandy Bridge clusters (Khan 2018) | Predicting plug power from RAPL: error (MAPE) 1.7 % to 1.8 % on Haswell with DRAM, 3.1 % without DRAM, 4.0 % to 4.3 % on Sandy Bridge, 7.7 % for DRAM alone. OS counters alone gave 5 % to 15 % |
| Haswell workstation, Plugwise (Khan 2018) | Correlation 0.99 between wall power and package power |
| Khan 2016 (search summary only) | P_wall about 1.212 x P_package + 25.58 W; maximum error 5.6 % across frequencies |
| Alder Lake desktop i9-12900K (2021; ICPE 2024) | Consistent overall, but at low power RAPL stayed near 1.5 W while the AC input varied. No DRAM domain, so memory-heavy loads read low. PP0 differed from the package by 0.35 W at idle |
| Whiskey Lake (our CPU) | **No study found**, on Windows or elsewhere |
| Broadwell DGX-1 (Jay 2023) | Wattmeter versus RAPL-based tools: slope 1.17 to 1.18, correlation about 0.95 |
| PSYS (Skylake and later, not all parts) | On three Linux laptops (ThinkPad L15 Gen1/Gen2, Alienware m17 R3) PSYS gave the same as an external wattmeter, with no error figures |
| AMD Zen 2 (EPYC 7502, 2021) | RAPL is modelled. Package "significantly lower" than the AC input: 170 W per processor against 489 to 509 W at the wall under full load (about 67 to 70 %, own calculation) |
| Server slides 2026 | RAPL 5 % to 43 % below IPMI on Xeon E5-2630 v4, EPYC 7452, 7513, 7643; the worst case was a single-socket EPYC 7643 (slides, not peer reviewed) |
| EMI itself | CodeCarbon: "not yet measured against an external reference". One author found EMI and an MSR driver 0.1 % to 0.7 % apart (single source) |

### 6.2 Package share of platform power

| System | Idle | Load | Source type |
|---|---|---|---|
| Core Ultra 7 265H laptop | 58 % of PSYS (package 3.85 W of 6.66 W) | 86 % (21.35 W of 24.69 W) | CodeCarbon docs (battery, PSYS) |
| Core i7-7600U laptop (Kaby Lake) | 12 % of PSYS (1.44 W of 12.21 W) | 52 % (15.73 W of 29.97 W) | CodeCarbon docs |
| Threadripper 1950X desktop (2017) | 39 % (38.6 W of about 100 W) | 62 % (about 172 W of about 280 W) | CodeCarbon docs |
| Dual Xeon Gold 6138 server | | 53 % to 66 % of system energy | 2026 slides |
| **Our HP 250 G7 (tested here)** | 24 % to 36 % (rest phases); 46 % to 51 % in the hand log and EnergyReader | 61 % to 67 % | Calibration run |

So the package is about **12 % to 86 %** of platform power, and a fixed percentage is wrong at idle. The model that fits best is affine: P_wall = a(model) + k x (P_package - P_package at idle), with k about 1.17 to 1.2.

### 6.3 Timing and counters

* RAPL updates about every 1 ms, values carry no timestamps. Sampling above about 20 per second cannot reduce the systematic error below 5 %.
* Skylake and Haswell counters are 32 bit and 61 microjoule per unit: they wrap after about 4.9 h at 15 W and 17 min at 250 W (own calculation: 2^32 x 61 uJ = about 262 kJ). EMI returns accumulated picowatt-hours with an arbitrary zero point. How EMI behaves at wrap, after sleep or hibernation is not documented.
* One author measured the RAPL hardware value changing about every 2 ms through EMI. Windows' default timer tick is 15.625 ms.
* Polling too often disturbs the measurement: on an Intel server the effect appeared from 10 Hz and rose to 25 to 49 W at 1000 Hz. A 5 s step (as in the client) is far below that.
* Intel "energy filtering" (after the PLATYPUS finding of 2020) adds noise: about 2 % at 1 s windows and 5 % to 15 % at 100 ms. For windows of 300 s it does not matter.

### 6.4 Battery fuel gauge

* Windows demands from an ACPI battery: reporting in mW and mWh, accuracy of 95 % or better, capacity granularity of at most 1 % of design capacity near the low levels and about 0.25 % (1/400) in the upper range. Sampling and averaging intervals are left to the maker.
* The only DAQ-based characterisation found is a ThinkPad T61 from 2010: the current was low-pass filtered with about 16 s delay and the RMS error was 19 %. No independent study of a modern laptop exists.
* Our HP showed steps of about 11 to 12 mWh every 10 s. At 4 W a 120 s phase drops about 133 mWh, so one step is a few percent.
* The battery sees the DC side only: no adapter losses. It does not exist on the charger or on a desktop.
* For a 300 s report at 2.3 W one interval is about 190 mWh (own calculation), that is one or two meter updates: a single report has a large relative error, but sums over an unbroken chain of readings are right, because the quantisation errors cancel.

### 6.5 Smart plugs

* Tasmota documents invalid readings below about 5 W on some chips (HLW8032, CSE7766) and advises against calibrating with computer equipment.
* Shelly Plus Plug S showed nothing below 2 W in one test (search summary only); a Gen3 review saw about 11 % at low load (single review).
* The only peer-reviewed study (e-Prime 2023): four of five brands had energy errors of 54 % to 100 % on fast-changing power-electronic loads (a PC power supply is one). Belkin stayed below 1.7 %.
* Rule: qualify every plug model against a laboratory meter at about 2, 5, 10, 25 and 50 W with a real PC load, and compare energy over long windows, not instant watts. A plug also uses about 0.5 to 1 W itself.

### 6.6 Other estimation methods

* `load x TDP` fallbacks (CodeCarbon) deviate from RAPL from about -60 % to +190 %.
* RAPL-only tools (Scaphandre, PowerJoular, CodeCarbon default) capture about 53 % to 66 % of server wall energy.
* SPECpower-based models (Green Metrics Tool XGBoost, Cloud Carbon Footprint) have no published wattmeter error and are trained on servers.
* Windows' own E3 does not claim to match the wall (Microsoft says so).

## 7. Recommendations for EcoWattSense (proposals)

Everything here is a **proposal**. Decisions belong to the project owner and the team.

1. **Keep `energy_uj` as it is.** It means energy at the wall socket. No reading available to a normal program is that. Writing RAPL or battery values into it would be silently wrong, because the server marks every sent value as "measured".
2. **Send the measured readings in separate fields.**
   * `battery_energy_uj` (existing field): charge difference x 3,600,000 µJ per mWh; leave it out (do not send 0) on the first report, after a change of power source, with no battery, with an unknown value (0xFFFFFFFF), with relative units, or after a gap.
   * `device_energy_uj` (existing field): minus the battery energy, only on battery and when the result is zero or above.
   * New field for the CPU package energy from EMI and a "source" marker (`emi`, `battery`, `none`). The names are open; adding a field is a separate pull request on both sides.
3. **Battery API for the Windows client:** `IOCTL_BATTERY_QUERY_STATUS` through P/Invoke needs no new package. WMI needs `System.Management`. WinRT needs a change of the target framework and was stale on our laptop. All three gave the same charge. The rate field is unusable on the HP, so use the charge difference.
4. **EMI reader (Windows 11) if the team decides to add it:** find the device with SetupAPI off the main thread (enumeration can stall on a slow ACPI call), open once with `GENERIC_READ`, share read and write, try all interfaces, use channel `RAPL_Package0_PKG` only and never sum channels, convert W = 0.036 x delta pWh / delta ticks, sum only positive deltas, skip samples with the same timestamp, treat every failure (including error 5) as "unknown" and log it once, never ask for administrator rights. A step of 5 s is fine.
5. **Do not use `EsifDeviceInformation` in the product.** It needs administrator rights, is undocumented, the unit comes from one test, and values jump. A LocalSystem helper would solve access but means an installer with administrator rights and privileged own code. Changing the WMI security descriptor is a security change and is not recommended. Do not read "Energy Meter" through .NET `PerformanceCounter` until a Windows 11 probe shows instances. Do not add third-party drivers or the AMD SDK now.
6. **Use measured data to improve the table per model, not to replace it.** For laptops: median measured watts per state from reports on battery. On Windows 11 laptops both sources together can teach the package-to-total relation on battery and apply it on the charger (without adapter losses; to be validated with a plug). Calibration needs series of intervals in the same state because the battery lags.
7. **Use the calibration program on reference laptops** to produce a model per laptop model (base, screen, CPU, graphics) from real readings. Our first run already shows the table is high at idle and low at full load for the HP 250 G7.
8. **Next tests (from the report):**
   * Windows 11 probe as a normal user on at least three Intel machines (one 8th generation, for example the HP after an update if the owner agrees), one AMD Ryzen and one machine managed by a university: EMI present or not, opens without administrator rights, channels, watts at rest and under load, EMI versus counters, owner of the EMI device, `Get-PnpDevice` for `SWC\VID8086_EMD_1.0`, PSYS channel present or not.
   * Battery and DTT side by side on the HP for at least 2 h, constant brightness, in phases: idle with screen, light work, 10 min full load, screen off; confirm the unit; explain the step difference.
   * A Lenovo with DTT: does `EsifDeviceInformation` exist, what error code a normal user gets (0x80070005 or 0x80041003), are participant 3 and 4 the same, DTT and Windows versions.
   * Smart-plug validation: each plug model against a lab meter, then plug on the HP on the charger and on one Windows 11 desktop, at least 2 h per state, with EMI, DTT and battery; fit P_wall = a + k x P_package; decide yes or no for server-side calibration.
9. **Decisions that belong to the owner (the report lists four):**
   * whether to add the CPU package energy and a source marker to the contract;
   * whether to accept that desktops and Windows 10 will long show only the model;
   * whether the tray app shows measured values (the task draft says yes);
   * whether to ask for a model identifier for calibration (privacy and contract; `machine_hash` cannot be read back).
   * Also: the server stores `battery_energy_uj` and `device_energy_uj` but the history API does not return them yet.

**Conclusion of the report.** The client is a calibration sensor, not a meter. Most of the fleet (desktops and Windows 10) will stay on the model for a long time. The value of the measured fields is in improving the table per model. Two results are not obvious: on battery, Microsoft's own E3 is 71 % top-up to the battery reading, so a laptop on battery is an unusually clean reference, while the same laptop on the charger is only a model; and EMI availability on Windows 11 may depend on whether Windows Update delivered a driver, which may differ between machines of one university.

## 8. Open points and what is not confirmed

### 8.1 EMI and Windows 11

* Whether a normal user opens EMI on Windows 11. Evidence is indirect (three programs, one author statement). The device security descriptor is not published. Restricted tokens and services under other accounts were not covered. **Not tested here.**
* Who provides the EMI device with RAPL: the in-box PPM driver (single source), the Intel `SWC\VID8086_EMD_1.0` component, or something else; and whether its presence depends on Windows Update. The parent device of `EMD` is unknown.
* The first Windows 11 build with RAPL-backed EMI. No Microsoft note says. Best guess "21H2 or an early 22H2" (inference). No generation list; **nothing at all about Whiskey Lake** on Windows 11.
* Whether channel `PSYS` (whole platform) appears through EMI on Windows. Neither Firefox nor Chromium maps it.
* Whether the "Energy Meter" counter set gives instances on Windows 11, which component registers it, its rights, its unit (milliwatts from one project), and how .NET `PerformanceCounter` behaves.
* EMI behaviour at counter wrap, after sleep or hibernation.
* VMs, VDI, VBS/HVCI and Arm: not tested. Expected: no device in guests; no data for Arm.
* The accuracy of EMI against an external meter, and the link between RAPL and wall power on laptops and client AMD parts.

### 8.2 DTT

* `EsifDeviceInformation`: unit and participant meaning come from one test on one laptop; the access-denied mechanism is unconfirmed (error code not saved); behaviour on Lenovo, Dell and Windows 11 unknown. 2026 DTT releases are Windows 11 only.

### 8.3 Battery

* Resolution and accuracy of modern fuel gauges: steps of 22 to 228 mWh in the hand log against 11 to 12 mWh per 10 s in the later probes (and 2,177 mWh in the hourly report). The hand-log spread is not explained. Other models may report the discharge rate.
* Package to total relation on our laptop: one hand log (14 minutes, about 46 %), the EnergyReader at rest, and the calibration run. No wall-socket measurement.
* Adapter losses are not seen by the battery.

### 8.4 Fleet and tools

* `energy_rates` for desktops: no measurement at all. ENERGY STAR values are maker declarations; "short idle" and "long idle" definitions and the column mapping were not verified.
* Fleet make-up of the university: Windows versions, processors, desktops against laptops, driver and Defender policies.
* AMD Ryzen Master Monitoring SDK (admin need, driver, CPU list, licence text) and Intel PMT (device access list, whether it holds package energy): the vendor pages did not answer; data from search summaries.
* Code details of Firefox, Chromium and CodeCarbon came from summaries of the fetch tool, not raw files. They must be checked in the raw sources before code is written.
* Plug accuracy at low loads: no controlled test; figures from documentation, search summaries and an abstract.
* Calibration program: the version with the real display-state reading is not yet tested on hardware; no valid "screen off" phase has been recorded yet, so base power and screen power at 50 % are unknown.
* The thermal-zone source gave a constant value; its use in the model is not decided.

## 9. Lessons from running the test

1. **Do not start the test program inside the Claude app's Windows job object.** The first calibration run at 17:06 was lost: the program was started from inside the app's process tree, and when the app restarted at 17:16 Windows ended everything in its job object, including the test. The fix: start the program through WMI `Win32_Process.Create`, so it is not a child of the app and has no shared job object.
2. **Save data during the run.** Nothing was on disk after the lost run. The program now writes the header of `samples.csv` and `phases.csv` at the start, appends a row after every sample and a phase row when a phase ends. If the program is killed, everything measured so far stays on disk. The final write adds the extra columns (DTT, thermal zones, Energy Meter) and the model files.
3. **The run at 17:26 worked for phases 1 to 6.** Phase 7 (screen off) was stopped after 23 s because input reached the machine while the display was off ("Invalid: input"). Everything before was kept.
4. **Read the display state from Windows, do not trust the command.** The program now registers for `GUID_CONSOLE_DISPLAY_STATE` (`RegisterPowerSettingNotification`, message `PBT_POWERSETTINGCHANGE`: 0 off, 1 on, 2 dimmed), writes the state into every sample, starts the settling time when the state first reports off, and marks "display stayed on" after 10 s without off or "display woke up". The display-off command (`SC_MONITORPOWER`) is sent to the program's own window first and only then, once more, to all windows with a timeout, so one window that does not answer cannot freeze it. **This version has not run on hardware yet.**
5. **Brightness 0 % is not off.** In phase 1 the lowest brightness still lights the screen (4.52 W against 4.85 W at 50 %). Only a real screen-off phase gives the base power.
6. **Keep the system awake but change no setting.** The program asks Windows to keep the system and display awake with `SetThreadExecutionState` during the test (the request ends with the test).
7. **Phase length and quantisation.** A 118 s phase at 4 W drops about 133 mWh, so one 11 mWh step is a few percent. Differences smaller than a step are noise. Make `PhaseSeconds` longer when numbers look noisy.
8. **Battery requirements for the test.** The charger must be out, the battery above 30 %; the test stops at 15 %, when the charger is plugged in, and on input during the screen-off phase.
9. **Administrator rights.** The program runs as a normal user (manifest `asInvoker`); only the DTT reading needs administrator rights, offered by a restart button.
10. **Data safety.** The result files hold maker, model and processor name only: no computer name, user name, serial number or device id.
