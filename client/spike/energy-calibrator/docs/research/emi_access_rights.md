# Energy Meter Interface (EMI) and "Energy Meter" performance counters: access for a normal (non-administrator) Windows user, from .NET

Method note (read first). The research was read-only: web pages only, nothing was run or installed, and no Windows probe was made. Microsoft Learn pages were read in full. Source-code files and GitHub pull-request or issue bodies were read through a fetch tool that summarizes pages with a small model, so code details below are paraphrased from those summaries and should be re-checked against the raw files before a final report states them as exact. Many "other program" reports come from small individual or automated-agent GitHub repositories; they are author-reported and not independently verified, and each is tagged "secondary". Source files were the default-branch heads as of November 2026. Direct quotes are kept to a minimum on purpose; most statements are paraphrases.

## 1. EMI device interfaces (GUID_DEVICE_ENERGY_METER {45BD8344-7ED6-49cf-A440-C276C933B053}): security descriptor, standard-user CreateFile(GENERIC_READ) and the IOCTLs, reports of ERROR_ACCESS_DENIED

### Takeaway
Microsoft publishes no access-control rule for EMI, so the security descriptor is whatever each EMI driver or INF sets (the generic default for device objects is full access for administrators and read/write/execute for everyone else). In practice, Firefox, Chromium and a Python tool (author-reported) open EMI with GENERIC_READ only, from unelevated processes on Windows 11, with no elevation code, and I found no report of ERROR_ACCESS_DENIED; but no source publishes the actual SDDL of an EMI interface.

### Cited Findings
- EMI is a driver interface available from Windows 10. Clients find devices with SetupDiEnumDeviceInterfaces and SetupDiGetDeviceInterfaceDetail; one device interface instance exists per present, EMI-compliant metering device; the GUID is {45BD8344-7ED6-49cf-A440-C276C933B053} (GUID_DEVICE_ENERGY_METER in emi.h). The documented client sequence is IOCTL_EMI_GET_VERSION, GET_METADATA_SIZE, GET_METADATA, then GET_MEASUREMENT; EMI V1 is Windows 10 and V2 is Windows 10 version 1809 and later. The page says nothing about permissions, security descriptors or elevation. — [Microsoft Learn: Energy Meter Interface](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/energy-meter-interface)
- IOCTL_EMI_GET_MEASUREMENT is defined as CTL_CODE(0x0022, 0x003, METHOD_BUFFERED, FILE_READ_ACCESS), value 0x0022400C, so the handle needs read access only. The page shows only this IOCTL; the codes of the other three IOCTLs were not displayed. — [NtDoc: IOCTL_EMI_GET_MEASUREMENT](https://ntdoc.m417z.com/ioctl_emi_get_measurement)
- Microsoft's IOCTL_EMI_GET_MEASUREMENT page says the EMI interface of any device is meant to be shared across the system, and that how often counters are sampled and accumulated depends on how often each consumer asks and on the driver. It has no access-control remarks. Minimum client is Windows 10. — [Microsoft Learn: IOCTL_EMI_GET_MEASUREMENT](https://learn.microsoft.com/en-us/windows/win32/api/emi/ni-emi-ioctl_emi_get_measurement)
- Generic WDM rule (not EMI-specific): access to a device is controlled by a security descriptor. The PnP manager applies a descriptor set in the registry for the device, else one set for the device setup class, else leaves the default, which is derived from device type and characteristics. For most device types the default gives administrators GENERIC_ALL and everyone else GENERIC_READ, GENERIC_WRITE and GENERIC_EXECUTE. Non-WDM drivers must supply their own default through IoCreateDeviceSecure, and class-GUID registry settings override it. — [Microsoft Learn: Controlling Device Access (WDM)](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/controlling-device-access)
- Firefox (parent process) opens each EMI interface path with CreateFile, desired access GENERIC_READ, share mode FILE_SHARE_READ | FILE_SHARE_WRITE, then calls the EMI IOCTLs; there is no elevation code and no comment about privileges. Details in question 3. — [gecko-dev PowerCounters-win.cpp](https://raw.githubusercontent.com/mozilla/gecko-dev/master/tools/profiler/core/PowerCounters-win.cpp)
- Chromium (EnergyMetricsProviderWin) does the same: CreateFile with GENERIC_READ, share read and write, OPEN_EXISTING, then IOCTL_EMI_GET_VERSION, GET_METADATA_SIZE, GET_METADATA and GET_MEASUREMENT; failures are only logged. Details in question 3. — [Chromium energy_metrics_provider_win.cc](https://raw.githubusercontent.com/chromium/chromium/main/components/power_metrics/energy_metrics_provider_win.cc)
- Secondary (author-reported): the codecarbon pull request that adds Windows EMI support (stdlib-only ctypes; enumerates GUID_DEVICE_ENERGY_METER devices) says it needs no admin rights and no kernel driver, and describes the result as "validated: reads succeed from an unelevated process" on a Windows 11 bare-metal Intel Core Ultra 7 265H, seeing RAPL_Package0_PKG, DRAM, PP0 and PP1 channels (about 4 W idle). The same PR says Windows 10 only reports on devices with dedicated metering hardware such as Surface Book, and that it does not work inside VMs. It claims Intel and AMD support, but only the Intel laptop is described as tested. — [mlco2/codecarbon PR #1263](https://github.com/mlco2/codecarbon/pull/1263)
- Secondary (author-reported): a Windows task-monitor project enumerates GUID_DEVICE_ENERGY_METER interfaces with SetupAPI, opens each once on a one-shot worker thread, reads version, metadata size and metadata, keeps only devices with a RAPL_Package<N>_PKG channel, and polls IOCTL_EMI_GET_MEASUREMENT per sample. Test host: Intel Core Ultra 7 255H laptop, Windows 11, one EMI device with a RAPL_Package0_PKG channel. The PR does not discuss privileges or access denied; a failed read is logged once and treated as zero energy. — [mgradwohl/tasksmack PR #2873](https://github.com/mgradwohl/tasksmack/pull/2873)
- Secondary (author-reported, PR still open, comparison "not independently verified"): a Windows EMI provider for green-metrics-tool says no custom kernel driver or test mode is required, and that the inbox Microsoft PPM driver on Windows 11 bridges RAPL MSRs to EMI automatically; one run on Windows 11 with an Intel CPU agreed with Scaphandre to under 1 percent. It does not say whether administrator rights are needed. — [green-coding-solutions/green-metrics-tool PR #1801](https://github.com/green-coding-solutions/green-metrics-tool/pull/1801)
- Primary (Mozilla developer, 17 June 2022): on Windows 11 the EMI data recorded as profiler counters is CPU RAPL data, similar to what Intel Power Gadget gave; on Windows 10 EMI only reports something if the machine has hardware power meters (example given: Surface Book 1). The work landed in mozilla-central on 30 June 2022, and a Firefox 104 release note about power analysis on Apple M1 and Windows 11 was requested in the bug. Nothing in the comments mentions admin, elevation or access denied. — [Bugzilla 1774844](https://bugzilla.mozilla.org/show_bug.cgi?id=1774844) (comments read through https://bugzilla.mozilla.org/rest/bug/1774844/comment)
- Windows' own Energy Estimation Engine (E3) consumes EMI: if a device exposes data through EMI and its rail names follow the documented taxonomy (CPU or CPU_*, STORAGE, WIFI, MBB, DISPLAY, GPU, NPU), E3 prefers that data over its software model. — [Microsoft Learn: Naming Convention for EMI Rails](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/rail_naming)

### Inferences
- The evidence is behavioural, not documentary. Three independent clients request only GENERIC_READ and carry no elevation path (Firefox parent process, Chromium browser process, a Python ctypes tool), and one of them states an unelevated success on Windows 11. So for the RAPL EMI device that Windows 11 exposes on Intel (and, per a Mozilla slide deck seen only as a search snippet, AMD Ryzen from Windows 11 22H2), a standard user very probably can open the interface with GENERIC_READ and call the four IOCTLs.
- That outcome matches the generic default descriptor (everyone gets read) and FILE_READ_ACCESS on the IOCTL, but the EMI driver owns the descriptor, so other vendors' EMI devices (Surface-class hardware meters on Windows 10, OEM drivers) could differ; nothing documents it.
- Tray-app consequences: request GENERIC_READ only (not read+write or GENERIC_ALL), use FILE_SHARE_READ | FILE_SHARE_WRITE (the interface is meant to be shared), enumerate all interfaces rather than only the first (Chromium has a TODO asking whether the first interface is always the right one), and treat a failed open as "unknown" while logging GetLastError (5 = ERROR_ACCESS_DENIED), since neither browser records the error code.
- Availability matters more than rights: on Windows 10 a RAPL EMI device is usually absent (Mozilla, codecarbon). This research session runs on Windows 10 Pro build 10.0.19045, where an EMI device would normally not exist unless the machine has dedicated meter hardware.

### Gaps
- No source publishes the security descriptor (SDDL) of an EMI device interface, and I could not inspect one (read-only, nothing run).
- Which driver creates the RAPL EMI device on Windows 11 is known only from an author-reported claim (inbox PPM driver); no Microsoft page found says so.
- No report of ERROR_ACCESS_DENIED for EMI was found. Searches covered the web, the GitHub issue search for IOCTL_EMI_GET_MEASUREMENT (4 hits) and GUID_DEVICE_ENERGY_METER (3 hits), and Bugzilla 1774844. Absence of reports is weak evidence because Firefox and Chromium do not capture GetLastError on open failure.
- AMD: the codecarbon PR claims AMD support, but no AMD hardware is described as tested; the Mozilla FOSDEM 2024 slides ([PDF](https://archive.fosdem.org/2024/events/attachments/fosdem-2024-2716-firefox-power-profiling-a-powerful-visualization-of-web-sustainability/slides/22726/FOSDEM_2024_-_Firefox_Power_Profiling_a_powerfu_Q635bzv.pdf)) were seen only in a search-result summary, not opened.
- Access from restricted tokens (AppContainer, low integrity, services under other accounts) was not covered by any source.
- Access flags of GET_VERSION, GET_METADATA_SIZE and GET_METADATA were not verified (only GET_MEASUREMENT was shown).

## 2. The "Energy Meter" performance counter set: provider, permissions, .NET PerformanceCounter versus PDH, non-English Windows

### Takeaway
I could not identify which component registers the "Energy Meter" counter set, and no source says whether a normal user can read it; Microsoft documents that V2 counter sets are read natively by PDH and only through a translation layer by the HKEY_PERFORMANCE_DATA registry API that .NET's PerformanceCounter uses. For non-English Windows, both PdhAddEnglishCounter and the .NET lookup (which tries the English "009" name table first) are locale-safe in principle, but reading "Energy Meter" from .NET is unverified.

### Cited Findings
- Counter-set naming (secondary, low reliability): one project reads a counter at path Energy Meter(RAPL_Package0_PKG)\Energy whose raw type is NumberOfItems64, in picowatt-hours, and its automated check found the sample inside the EMI V2 RAPL_Package0_PKG energy bracket. — [Unjuno/agent-interface PR #7758](https://github.com/Unjuno/agent-interface/pull/7758)
- Counter-set naming (secondary, author says untested on real hardware): another project reads \Energy Meter(*)\Power in milliwatts through PDH, with RAPL_Package0_PKG, PP0, PP1, DRAM and PSYS instances and other EMI meters keeping their own instance names, under the Local Service account; its author lists as unchecked "whether the Local Service account may read them on every machine". — [Programmer-Den/den-watcher PR #91](https://github.com/Programmer-Den/den-watcher/pull/91)
- The Microsoft EMI, Power Metering and Budgeting overview, and UMPS pages I read do not mention an "Energy Meter" counter set. The overview describes the older Power Meter route (ACPI 4.0 metering objects, ACPIPMI.SYS, the User-Mode Power Service exposing WMI classes that PerfMon uses), and the EMI page says energy meters are distinct from the Power Meter Interface. — [Overview of the Power Metering and Budgeting Infrastructure](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/overview-of-the-power-metering-and-budgeting-infrastructure); [User-Mode Power Service](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/user-mode-power-service); [Energy Meter Interface](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/energy-meter-interface)
- Microsoft's counter architecture page: a V1 provider is a performance DLL installed via .ini; a V2 provider publishes through the provider APIs and is installed via a .man manifest; V2 providers are user-mode programs (often services) or kernel-mode drivers, and requests go through the PCW.sys kernel extension. — [Microsoft Learn: About Performance Counters](https://learn.microsoft.com/en-us/windows/win32/perfctrs/about-performance-counters)
- Same page, consumers: PDH uses the registry APIs for V1 providers and the V2 consumer APIs for V2 providers; the HKEY_PERFORMANCE_DATA registry API supports V1 directly and V2 only indirectly through a translation layer that uses the V2 consumer APIs, and is described as not recommended for new code. Counters are described as not designed for collection more than once per second. — [Microsoft Learn: About Performance Counters](https://learn.microsoft.com/en-us/windows/win32/perfctrs/about-performance-counters)
- .NET (dotnet/runtime) PerformanceCounterLib reads counter and help name tables from the registry values "Counter <lcid>" and "Explain <lcid>", builds its category table from a "Global" HKEY_PERFORMANCE_DATA query, reads a category's samples by the category's name index, parses instances from PERF_INSTANCE_DEFINITION (duplicate names get a "#n" suffix), and contains no PDH or V2 or counter-set code. It converts an UnauthorizedAccessException from the performance key into Win32Exception(ERROR_ACCESS_DENIED) for old-version compatibility, and comments nothing about Performance Monitor Users or administrators. — [PerformanceCounterLib.cs](https://raw.githubusercontent.com/dotnet/runtime/main/src/libraries/System.Diagnostics.PerformanceCounter/src/System/Diagnostics/PerformanceCounterLib.cs); [PerformanceCounterCategory.cs](https://raw.githubusercontent.com/dotnet/runtime/main/src/libraries/System.Diagnostics.PerformanceCounter/src/System/Diagnostics/PerformanceCounterCategory.cs) (the category class only delegates to the lib)
- Same source, localization: CategoryExists, CounterExists and GetCategorySample consult the English library ("009", culture "en") first and then walk the current culture and its parents up to the invariant culture; a miss throws InvalidOperationException (or CategoryExists returns false). — [PerformanceCounterLib.cs](https://raw.githubusercontent.com/dotnet/runtime/main/src/libraries/System.Diagnostics.PerformanceCounter/src/System/Diagnostics/PerformanceCounterLib.cs)
- Real-world .NET use on a provider-based set: C# answers read the "GPU Engine" category with PerformanceCounterCategory.GetInstanceNames and GetCounters, with a reported caveat that NextValue can be wrong for delta-type counters and NextSample should be used (search-result summaries; pages not opened). — [Stack Overflow mirror](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/56830434/c-get-total-usage-of-gpu-in-percentage); [Qiita](https://qiita.com/mofurune/items/38daa7bb61babbe46740)
- A small C# sample enumerates categories with PerformanceCounterCategory.GetCategories, filters by name, and reads "Thermal Zone Information" with GetCounters and NextValue on two laptops (HP ProBook G7, Acer Nitro 5); Windows version and user account are not stated. — [nikvoronin/AllPerformanceCounters](https://raw.githubusercontent.com/nikvoronin/AllPerformanceCounters/main/README.md)
- Secondary: a developer reports that \Thermal Zone Information(*)\High Precision Temperature is the source that works without administrator. — [BarganConstantin/ccdeck issue #747](https://github.com/BarganConstantin/ccdeck/issues/747)
- PDH localization: PdhAddEnglishCounterW (Windows Vista and later) adds a language-neutral counter path, whereas PdhAddCounter needs a localized path. A nonexistent instance does not make it fail (it returns success). With a wildcard, the non-wildcard parts are localized but the wildcard is not expanded; Microsoft's procedure is PdhAddEnglishCounter, then PdhGetCounterInfo to get the localized full path, then PdhExpandWildCardPath, then PdhAddCounter on each result. — [Microsoft Learn: PdhAddEnglishCounterW](https://learn.microsoft.com/en-us/windows/win32/api/pdh/nf-pdh-pdhaddenglishcounterw)
- Registry-path permissions: access to HKEY_PERFORMANCE_DATA depends on read access to the PerfLib registry key. In July 2007 Mark Russinovich reported that on Windows Vista a standard user lacked it (only the new Performance Log Users and Performance Monitor Users groups and administrators were granted), that he got Interactive Users added back for Vista SP1 and Windows Server 2008, and that protecting counter data is the data source's job, not the key's. — [Russinovich, The Case of the Unexpected PsList Error](https://learn.microsoft.com/en-us/archive/blogs/markrussinovich/the-case-of-the-unexpected-pslist-error)
- The current .NET PerformanceCounter documentation page contains no statement about Performance Monitor Users or administrator rights; it only covers PerformanceCounterPermission. — [Microsoft Learn: PerformanceCounter Class](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.performancecounter)

### Inferences
- Because Microsoft says the registry API reaches V2 sets through a translation layer, and because C# programs read provider-based categories such as "GPU Engine" (a Windows graphics-driver counter set that I believe is V2, not confirmed by a source I read), .NET's PerformanceCounter probably can see "Energy Meter" if the set is registered and its names are in the "009" table. This is untested for "Energy Meter" specifically. A runtime probe would be PerformanceCounterCategory.Exists("Energy Meter"), then GetInstanceNames, then reading the raw value with NextSample().RawValue instead of NextValue.
- Non-English Windows: .NET tries English names first, and PDH has PdhAddEnglishCounter, so English category and counter names ("Energy Meter", "Power", "Energy") should work on a Polish or other localized Windows. Instance names such as RAPL_Package0_PKG look like EMI channel names (Firefox matches those literals against EMI metadata), so they are not localized resources.
- Access for a normal interactive user on the registry path depends on the PerfLib key ACL; Russinovich's report implies that since Vista SP1 an interactive standard user can read it, but this was not confirmed for Windows 10 and 11. Whether the V2 "Energy Meter" set adds its own restriction is unknown; no source reports an access-denied case for it.
- Practical reading paths, from the lowest overhead and fewest assumptions: (1) direct EMI IOCTLs (question 1), no localization and no counter-registry dependency; (2) PDH with PdhAddEnglishCounter on \Energy Meter(*)\Power and \Energy, which Microsoft names as the preferred consumer for V2 sets; (3) .NET PerformanceCounter, which depends on the registry translation layer, the English-name table and a heavy "Global" query to build its category table (the .NET code builds it from a Global read), so it suits one-off enumeration more than frequent polling. Microsoft says counters should not be sampled more often than once per second.

### Gaps
- Provider of the "Energy Meter" counter set: not found in Microsoft documentation or search; unknown whether it is a kernel (PCW) provider, a service, or which binary and Windows version. Microsoft's EMI and PMB pages do not describe the set.
- No source states whether reading the set needs Performance Monitor Users membership or administrator rights; the Local Service case is explicitly unverified by the one project that reads it.
- No source confirms that PerformanceCounterCategory.GetCategories lists "Energy Meter" or that the .NET reader handles it; no .NET sample for it was found.
- Whether the set exists on Windows 10 machines without hardware meters is unknown (EMI itself is absent there per Mozilla and codecarbon).
- The current default ACL of the PerfLib key on Windows 10 and 11, and any per-counter-set security of V2 providers, were not retrieved. The TechNet statement that Performance Monitor Users can view real-time data ([TechNet](https://technet.microsoft.com/en-us/library/cc749154.aspx)) was seen only as a search snippet and concerns Windows 7 era guidance.
- No test on a non-English Windows exists in any source; the localization conclusion rests on reading the .NET and PDH code and documentation.

## 3. What Firefox, Chromium and other normal-user programs do with EMI (code paths, comments about privileges or sandbox)

### Takeaway
Both browsers read EMI in their unsandboxed, user-privilege main process (Firefox parent process; Chromium browser process, which is the sandbox broker at Medium integrity), open the device with GENERIC_READ only, and contain no comment or code about administrator rights, privileges, sandboxing or ERROR_ACCESS_DENIED.

### Cited Findings
- Firefox PowerCounters-win.cpp: includes emi.h, setupapi.h and devioctl.h; hard-codes the EMI GUID because, per its comment, the GUID_DEVICE_ENERGY_METER symbol does not exist before Windows 10 at compile time; no runtime Windows version check. — [gecko-dev PowerCounters-win.cpp](https://raw.githubusercontent.com/mozilla/gecko-dev/master/tools/profiler/core/PowerCounters-win.cpp)
- Firefox gate: the PowerCounters constructor returns immediately unless XRE_IsParentProcess(); the comment says energy meters are global, so they are sampled only in the parent process. — [gecko-dev PowerCounters-win.cpp](https://raw.githubusercontent.com/mozilla/gecko-dev/master/tools/profiler/core/PowerCounters-win.cpp)
- Firefox enumeration and open: SetupDiGetClassDevs with DIGCF_PRESENT | DIGCF_DEVICEINTERFACE, SetupDiEnumDeviceInterfaces in a loop, SetupDiGetDeviceInterfaceDetail; then each PowerMeterDevice calls CreateFile with GENERIC_READ and FILE_SHARE_READ | FILE_SHARE_WRITE. If the handle is INVALID_HANDLE_VALUE the constructor returns silently (no GetLastError, no log), leaving a device with no channels. — [gecko-dev PowerCounters-win.cpp](https://raw.githubusercontent.com/mozilla/gecko-dev/master/tools/profiler/core/PowerCounters-win.cpp)
- Firefox device gating and use: EMI version must be V1 or V2, metadata size nonzero, allocations and IOCTLs must succeed (IOCTL_EMI_GET_VERSION, GET_METADATA_SIZE, GET_METADATA, GET_MEASUREMENT per sample); a device without channels is dropped with an NS_WARNING. Channel names matched are RAPL_Package0_PKG (label "Power: CPU package"), RAPL_Package0_PP0 (CPU cores), RAPL_Package0_PP1 (iGPU), RAPL_Package0_DRAM and RAPL_Package0_Core%u_CORE. The file has no comment about administrator rights, privileges, sandbox or access denied, and no PDH or perf-counter code. — [gecko-dev PowerCounters-win.cpp](https://raw.githubusercontent.com/mozilla/gecko-dev/master/tools/profiler/core/PowerCounters-win.cpp)
- Mozilla user docs: the older "Power profiling" overview page names Intel Power Gadget as the Windows tool and does not mention EMI, Windows versions or permissions; the Q3 2022 profiler blog says only that new Windows 11 and Apple Silicon capabilities let the profiler capture Firefox power use, enabled with the Power preset. — [Firefox Source Docs: Power profiling](https://firefox-source-docs.mozilla.org/performance/power_profiling_overview.html); [Mozilla Performance blog, Q3 2022](https://blog.mozilla.org/performance/2022/10/27/whats-new-with-the-firefox-profiler-q3-2022/)
- Chromium EnergyMetricsProviderWin::Initialize: SetupDiGetClassDevs(GUID_DEVICE_ENERGY_METER, DIGCF_PRESENT | DIGCF_DEVICEINTERFACE); takes the first device interface from SetupDiEnumDeviceInterfaces (a TODO, crbug.com/40879127, asks whether the first interface is always the right one); SetupDiGetDeviceInterfaceDetail for the path; CreateFile with GENERIC_READ, FILE_SHARE_READ | FILE_SHARE_WRITE, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL. Failures are logged with PLOG: GET_VERSION failure at warning level with the text "EMI interface not available", the other IOCTLs at error level. No comment or code about privileges, administrator rights, sandboxing, access denied or the "Energy Meter" perf counters. — [Chromium energy_metrics_provider_win.cc](https://raw.githubusercontent.com/chromium/chromium/main/components/power_metrics/energy_metrics_provider_win.cc)
- Chromium header: EnergyMetricsProvider provides system-wide energy consumption metrics; Create() returns nullptr when no suitable implementation exists; CaptureMetrics returns nullopt when unavailable; field comments say GPU energy is only available on client CPUs and DRAM energy only on server CPUs, with separate AMD fields; no process or sandbox notes. — [Chromium energy_metrics_provider.h](https://raw.githubusercontent.com/chromium/chromium/main/components/power_metrics/energy_metrics_provider.h)
- Chromium sandbox design doc: the broker is always the browser process; the browser, crash handler and network utility processes run at Medium integrity (as of M75); renderers run at Untrusted integrity and almost all resources they use are acquired by the browser and handed over. — [Chromium docs/design/sandbox.md](https://raw.githubusercontent.com/chromium/chromium/main/docs/design/sandbox.md)
- Other normal-user programs (all secondary): codecarbon (Python ctypes, unelevated validation on Windows 11), the tasksmack task monitor (C++ SetupAPI, one-shot worker thread to open), green-metrics-tool provider (open PR). See question 1 for links and details. A separate project reads the counter set through PDH instead of the IOCTLs (see question 2).

### Inferences
- Neither browser has special privilege handling for EMI: on Windows 11 the same code path works for the ordinary signed-in user. Because the sandbox broker is the browser process, EMI reading in Chromium most likely happens in the browser process and not in sandboxed renderers; I did not verify the call site.
- The silent-failure design in both browsers (no GetLastError, a TODO about multiple interfaces) means their code is not evidence that every device allows opening; it is evidence that the common Windows 11 RAPL device does.

### Gaps
- The call site and process of Chromium's EnergyMetricsProvider (and any other Chromium process that might use it) was not checked.
- Code facts come from a summarizing fetch tool, not a direct read; exact lines should be re-verified.
- No Firefox or Chromium bug about EMI access denied was found; a Bugzilla search with a combined query returned no rows, and only the single bug 1774844 was read.

## 4. Microsoft documentation on EMI access control (device interface property, INF security setting for energy meter drivers)

### Takeaway
I found no Microsoft page that defines access control for EMI; the EMI pages describe only discovery and IOCTLs. The only applicable Microsoft mechanism is the generic one: a driver or its INF sets the security descriptor of the device (and device class), with a documented default of full access for administrators and read/write/execute for everyone else.

### Cited Findings
- The Power Metering and Budgeting documentation folder holds energy-meter-interface, power-meter-interface, acpi-power-meter-interface, overview-of-the-acpi-4-0-power-metering-objects, overview-of-the-power-metering-and-budgeting-infrastructure, rail_naming, software-defined-batteries, user-mode-power-service and acpi-ipmi-operation-region; there is no separate EMI driver-implementation or security page. — [GitHub contents listing of MicrosoftDocs/windows-driver-docs powermeter folder](https://api.github.com/repos/MicrosoftDocs/windows-driver-docs/contents/windows-driver-docs-pr/powermeter)
- The EMI overview and the IOCTL_EMI_GET_MEASUREMENT reference describe discovery by SetupDi calls, the IOCTL sequence and the sharing intent, and contain no section on access, security or elevation. — [Energy Meter Interface](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/energy-meter-interface); [IOCTL_EMI_GET_MEASUREMENT](https://learn.microsoft.com/en-us/windows/win32/api/emi/ni-emi-ioctl_emi_get_measurement)
- The generic rule for who can open a device (registry security descriptor of the device, then of the setup class, then the type-based default; IoCreateDeviceSecure for non-WDM drivers; class-GUID registry settings override the driver's default) is documented under Controlling Device Access, which links to "Setting Device Object Properties in the Registry" for how to set a descriptor. — [Microsoft Learn: Controlling Device Access (WDM)](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/controlling-device-access)
- A Windows component, E3, is a documented EMI consumer (rail naming taxonomy), which shows EMI is meant to be consumed by system code and clients generally. — [Naming Convention for EMI Rails](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/rail_naming)

### Inferences
- Access to a particular EMI interface is decided by the implementing driver's INF or code, so the useful question for a given machine is which driver exposes the interface and what descriptor it set; Microsoft's EMI documentation cannot answer it.

### Gaps
- No Microsoft documentation of an EMI-specific device interface property, INF security directive or Hardware Lab Kit requirement about who may read EMI was found.
- Microsoft's DDI reference pages for the other IOCTLs and for emi.h structures were not read.

## 5. WMI classes carrying power or thermal data (root\wmi EsifDeviceInformation): "Access denied", WMI data-block security, supported non-security-weakening paths

### Takeaway
Microsoft documents that every WMI GUID has a security descriptor whose default (Windows Server 2003 and later) allows administrators only, and that a driver's INF can supply a different one; independent reverse-engineering places those descriptors in HKLM\SYSTEM\CurrentControlSet\Control\WMI\Security. Developer reports show root\WMI EsifDeviceInformation returning "Access denied" without administrator rights, but I could not confirm that this class is a driver data block governed by that registry key, and I found no Microsoft-documented way for an ordinary user program to get access other than the driver vendor's INF descriptor or an administrator-side security change.

### Cited Findings
- Microsoft: a security descriptor is associated with every WMI GUID; for Windows XP and earlier the default allowed full access to all users, and for Windows Server 2003 and later the default allows access only to administrators. A driver that defines WMI classes can include an INF DDInstall.WMI section whose Security directive stores a descriptor in the registry for the class GUID; flag SCWMI_CLOBBER_SECURITY controls replacing an existing descriptor. — [Microsoft Learn: INF DDInstall.WMI Section](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/inf-ddinstall-wmi-section)
- Microsoft: for custom WMI data blocks the system supplies a default security descriptor for all WMI class GUIDs, and alternate descriptors can be given in the device's INF. — [Microsoft Learn: Implementing Custom WMI Blocks](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/implementing-custom-wmi-blocks)
- Independent analysis (page is mainly about ETW providers and loggers): permissions are stored under HKLM\System\CurrentControlSet\Control\WMI\Security as REG_BINARY values named by the GUID without braces, holding self-relative security descriptors; a special value 0811c1af-7a07-4a06-82ed-869455cdf713 is the default for objects without their own entry; the kernel's built-in default gives Administrators, SYSTEM, LOCAL SERVICE and NETWORK SERVICE full control and Users only TRACELOG_REGISTER_GUIDS. The rights are WMIGUID_QUERY 0x1, WMIGUID_SET 0x2, WMIGUID_NOTIFICATION 0x4, WMIGUID_READ_DESCRIPTION 0x8, WMIGUID_EXECUTE 0x10 and the TRACELOG_* rights. The page does not mention Performance Monitor Users or data blocks. — [Geoff Chappell: ETW security](https://geoffchappell.com/notes/windows/etw/security.htm)
- Secondary (single machine, individual developer): a Windows thermal reader tested "root\WMI EsifDeviceInformation" and got 7 participants at 42 to 69 degrees C, with the entry marked "Access denied" in its admin column; the same project later says the source "is Access denied without admin"; on that machine the esifsvc service was running and an "Intel(R) Dynamic Tuning Processor Participant" device was OK. In the same table MSAcpi_ThermalZoneTemperature is marked as needing admin and as "Not supported" even elevated on that machine. — [BarganConstantin/ccdeck PR #751](https://github.com/BarganConstantin/ccdeck/pull/751); [ccdeck PR #752](https://github.com/BarganConstantin/ccdeck/pull/752)
- Secondary: the same developer reads the thermal counter set \Thermal Zone Information(*)\High Precision Temperature instead, with no privileges, where before the value came through a namespace that requires administrator. — [ccdeck PR #751](https://github.com/BarganConstantin/ccdeck/pull/751); [ccdeck issue #747](https://github.com/BarganConstantin/ccdeck/issues/747)
- Secondary: another project (XiControl) states its temperatures were read only through Intel DPTF root\wmi EsifDeviceInformation before it added an ACPI thermal-zone path for non-Intel machines; it does not discuss privileges. — [Oksion/XiControl PR #47](https://github.com/Oksion/XiControl/pull/47)
- Secondary: reading the same developer's other route, a hardware monitor that is already running and publishes plain HTTP on localhost, is described as needing no privileges to read. — [ccdeck PR #752](https://github.com/BarganConstantin/ccdeck/pull/752)
- Secondary and weak: root\wmi MSAcpi_ThermalZoneTemperature gives access denied to non-administrators in forum reports, and Stack Overflow answers for a non-admin approach all needed admin. — [python-forum.io thread](https://python-forum.io/printthread.php?tid=2762); [Stack Overflow mirror](https://windows-hexerror.linestarve.com/q/so64996339-Get-CPU-and-GPU-Temp-Using-Python-WITHOUT-ADMIN-ACCESS)
- WMI error semantics (search-result summary of the Microsoft page; page not opened): 0x80070005 means denied by DCOM security, 0x80041003 means denied by the provider or by namespace permissions, and namespace security can be edited in wmimgmt.msc. — [Microsoft Learn: WMI troubleshooting](https://learn.microsoft.com/en-us/windows/desktop/wmisdk/wmi-troubleshooting)
- Search-result summary only: an Intel Community reply says the Dynamic Platform and Thermal Framework driver is supplied by the PC maker (OEM). — [Intel Community thread](https://community.intel.com/t5/Mobile-and-Desktop-Processors/Intel-Dynamic-Tuning-question-dptf-error-id-17/m-p/1547607)

### Inferences
- An "Access denied" from a driver-backed root\wmi class for a standard user fits Microsoft's default (administrators only) when the driver's INF sets no other descriptor, and the Chappell page gives the registry location where such descriptors live. But it is equally possible that the denial is a namespace or provider check; the exact error code (0x80070005 versus 0x80041003) and the class GUID were not recorded in any source, so the "data-block security" explanation is likely but unconfirmed for EsifDeviceInformation.
- The only Microsoft-documented way to make a WMI data block readable by standard users is for the driver vendor to ship an INF Security descriptor (for ESIF, Intel or the PC OEM); changing the descriptor by hand or editing namespace security is a security-policy change made by an administrator, not something an application can do for itself, and this note does not recommend it.
- For a user-mode tray app the facts point to non-WMI sources for power and thermal data: EMI IOCTLs or the "Energy Meter" counters for energy, and the "Thermal Zone Information" counter set for temperature (reported to work without administrator on one developer's machine).

### Gaps
- No Microsoft or Intel documentation of the EsifDeviceInformation class (GUID, provider, whether it is a WDM data block or a MOF provider class) was found; an attempt to list Intel's dptf repository for the MOF failed (404 on the guessed path).
- Whether a security descriptor entry for that GUID exists in the WMI Security registry key on affected machines is unknown; nothing was run.
- No supported pattern (for example a privileged helper service) is documented by Microsoft or Intel for exposing ESIF data to standard users; none was found.
- The ccdeck table's "admin?" column is ambiguous (the "Access denied" text sits in it), so the exact per-user results come from the project's PR prose, not from the table.
