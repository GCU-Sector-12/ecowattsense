# Windows 11 processor energy (RAPL) through the Energy Meter Interface (EMI): builds, driver, CPU coverage, channels and real-world tool reports (state as of November 2026)

> Reading guide. [older: YEAR] marks information from 2022-2024 that may have changed. [single-source] marks a claim that rests on one author and was not independently confirmed. [snippet-only] marks a fact taken from a search-result snippet; I did not open that page. Wording is paraphrased on purpose (one short verbatim quote is used, in section 2, because exact wording matters there). Identifiers (channel names, counter paths, GUIDs, IOCTL names) are copied exactly. The text of the FOSDEM 2024 slides was extracted locally with pdftotext into a local text file (not kept) so slide statements could be re-checked.

## 1. Which Windows 11 version/build first exposed RAPL through EMI (21H2, 22H2, 23H2, 24H2)? Was it ever back-ported to Windows 10?

### Takeaway
No source names the first Windows 11 build that carries RAPL-backed EMI. The earliest dated public evidence is Mozilla's note of 17 June 2022 that Windows 11 returns CPU RAPL data through EMI (Intel); AMD Ryzen is first documented on Windows 11 22H2 (October 2022). On Windows 10, every source says EMI returns energy only on devices with real metering hardware (Surface Book 1, Surface 3); no source reports a back-port of RAPL to Windows 10.

### Cited Findings
- EMI is an old interface: drivers may implement it from Windows 10 on; version V1 is Windows 10, version V2 (several named channels per device) arrived in Windows 10 version 1809. Microsoft documents only the client contract (device interface, IOCTLs, units). The page says nothing about processors, RAPL or Windows 11; its docs metadata shows a last update of July 2025. — [Microsoft Learn: Energy Meter Interface](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/energy-meter-interface); the V2 structures are listed as available from Windows 10 version 1809 in [EMI_METADATA_V2](https://learn.microsoft.com/en-us/windows/win32/api/emi/ns-emi-emi_metadata_v2) and [EMI_CHANNEL_V2](https://learn.microsoft.com/en-us/windows/win32/api/emi/ns-emi-emi_channel_v2); the measurement struct is listed as available from Windows 10 in [EMI_CHANNEL_MEASUREMENT_DATA](https://learn.microsoft.com/en-us/windows/win32/api/emi/ns-emi-emi_channel_measurement_data).
- [older: 2022-06-17] First recorded statement about Windows 11: Florian Quèze (Mozilla) writes in the bug that adds EMI power data to the Firefox Profiler that on Windows 11 EMI reports RAPL data from the CPU (comparable to what Intel Power Gadget gave before), while on Windows 10 it reports something only if the machine has hardware power meters, for example the Surface Book 1. No Windows build number is given. — [Bugzilla 1774844](https://bugzilla.mozilla.org/show_bug.cgi?id=1774844) (comment list read through the bug's REST comment endpoint).
- [older: 2022] The first EMI patch landed in mozilla-central on 2022-06-29 (it was backed out for an unrelated test failure and re-landed the same day). — [gecko-dev commit list for PowerCounters-win.cpp](https://api.github.com/repos/mozilla/gecko-dev/commits?path=tools/profiler/core/PowerCounters-win.cpp&per_page=30). A search summary of the bug page says it was fixed in Firefox 104. — [Bugzilla 1774844](https://bugzilla.mozilla.org/show_bug.cgi?id=1774844)
- [older: 2022-08-17] The proposed Firefox 104 release note limited website power profiling to Apple M1 and Windows 11. — [Bugzilla 1774844](https://bugzilla.mozilla.org/show_bug.cgi?id=1774844). Mozilla's Q3 2022 profiler post says power capture relies on new capabilities in Windows 11 and Apple Silicon. — [Mozilla Performance blog](https://blog.mozilla.org/performance/2022/10/27/whats-new-with-the-firefox-profiler-q3-2022/)
- [older: 2022-10] The profiler's help text for the Power feature originally named only Windows 11 and Apple Silicon; Linux x86_64 and Intel Macs were added in Firefox 107. — [Bugzilla 1795047](https://bugzilla.mozilla.org/show_bug.cgi?id=1795047); FOSDEM slide 35 says Windows 11 and Apple Silicon since Firefox 104, Linux and Intel Macs since 107. — [FOSDEM 2024 slides](https://archive.fosdem.org/2024/events/attachments/fosdem-2024-2716-firefox-power-profiling-a-powerful-visualization-of-web-sustainability/slides/22726/FOSDEM_2024_-_Firefox_Power_Profiling_a_powerfu_Q635bzv.pdf)
- [older: 2022-10-27] First AMD datapoint: Quèze captured EMI power tracks on Windows 11 22H2 with an AMD Ryzen 7 5800U; the channels were RAPL_Package0_PKG plus one RAPL_Package0_CoreN_CORE channel per physical core (N = 0, 2, 4, 6, 8, 10, 12, 14). — [Bugzilla 1797697](https://bugzilla.mozilla.org/show_bug.cgi?id=1797697)
- [older: Feb 2024] FOSDEM slide 32 lists three Windows tiers: Windows 10 on devices with hardware power meters (Surface Book 1, Surface 3; CPU, GPU and Wi-Fi power); Windows 11 on Intel CPUs (CPU, GPU, DRAM power); Windows 11 22H2 on AMD Ryzen CPUs (CPU only, one track per core). Slide 16 says the Windows 10 sources are Maxim power meters in Surface Book 1 and Surface 3, and that many other devices declare such a meter in their ACPI tables without the chip being fitted. Slide 18 says only some machines report energy-meter channels with familiar (RAPL) names, namely Windows 11 with Intel CPUs. — [FOSDEM 2024 slides](https://archive.fosdem.org/2024/events/attachments/fosdem-2024-2716-firefox-power-profiling-a-powerful-visualization-of-web-sustainability/slides/22726/FOSDEM_2024_-_Firefox_Power_Profiling_a_powerfu_Q635bzv.pdf)
- [older: 2023-04-14] The Chromium commit that created the cross-platform EnergyMetricsProvider says it works only on Windows 11 for now (Chromium bug 1385251; no build or CPU named). — [Chromium commit 56f5ee5](https://github.com/chromium/chromium/commit/56f5ee5)
- [2026] CodeCarbon's Windows backend `windows_emi`: documentation says EMI reports CPU power only on Windows 11 on bare metal, and on Windows 10 only on devices with dedicated metering hardware (Surface Book given as the example). — [CodeCarbon methodology](https://docs.codecarbon.io/latest/explanation/methodology/); the 2026-07-05 proposal in issue 457 says the same (Windows 11 only; Windows 10 only with physical metering hardware). — [codecarbon issue 457](https://github.com/mlco2/codecarbon/issues/457)
- [2026] power-overwhelming (University of Stuttgart VISUS) recommends its `emi_sensor` over its own unsigned-driver `msr_sensor` on Windows 11 and on select Surface models running Windows 10; the main README adds that the sensor may exist on some Windows 10 installations (availability not guaranteed) and refers to a Firefox-team presentation for the need for special hardware. — [pwrowgrapldrv README](https://raw.githubusercontent.com/UniStuttgart-VISUS/power-overwhelming/master/pwrowgrapldrv/README.md), [main README](https://raw.githubusercontent.com/UniStuttgart-VISUS/power-overwhelming/master/README.md)
- [older: 2022, date inferred from the Firefox 104 post title] The Green Metrics Tool team (Linux/macOS only at that time) wrote that Firefox 104 queries EMI on Windows and that Windows 10 seems to work only where a power-meter chip is installed (Surface Book 1). — [green-coding.io blog](https://www.green-coding.io/blog/firefox-104-energy-measurements/)
- [2026] Recent confirmations on Windows 11 without a build number: Intel Core Ultra 7 255H laptop in tasksmack (Oct 2026) and an unnamed Intel CPU in the Green Metrics Tool EMI provider pull request (Sep-Nov 2026). — [tasksmack PR 2873](https://github.com/mgradwohl/tasksmack/pull/2873), [green-metrics-tool PR 1801](https://github.com/green-coding-solutions/green-metrics-tool/pull/1801)
- [older: 2024] Mozilla enabled power measurements on Windows 11 in its performance CI (bugs for Raptor/pageload power tests, Jul-Nov 2024); the bug text names neither CPU nor build. — [Bugzilla 1910874](https://bugzilla.mozilla.org/show_bug.cgi?id=1910874), [Bugzilla 1925593](https://bugzilla.mozilla.org/show_bug.cgi?id=1925593)

### Inferences
- Mozilla's first note is dated June 2022. From general knowledge (not sourced in this research) the only generally available Windows 11 release then was 21H2 (build 22000) and 22H2 (build 22621) reached general availability later in 2022. So RAPL-backed EMI existed in 21H2 or in a 22H2 preview at that date, but the sources never state which build was used. Treat "since 21H2 or an early 22H2" as the best-supported guess, not a fact.
- The explicit "22H2" on the AMD line (slide 32 and the 5800U capture) suggests AMD coverage was seen from 22H2 on; whether 21H2 lacks AMD is not established.
- From 2023 to 2026 every source says just "Windows 11", with no build qualifier. That fits a stable in-box capability present in 22H2 and later (23H2, 24H2, 25H2), but no source tests those builds separately.
- Several sources (the Mozilla bug and slides, CodeCarbon, power-overwhelming, the GMT blog) agree that Windows 10 only gets EMI data from hardware meters; they partly cite one another, so they are not fully independent. Together with the caller's observation (Windows 10 22H2, i5-8265U: counter set exists, zero instances) this points to "no RAPL EMI device on Windows 10"; a back-port through a cumulative update is not reported anywhere.

### Gaps
- No Microsoft release note, Windows Insider flight note, KB article or documentation says which build added a RAPL-backed EMI device. I searched Microsoft Learn and the open web.
- The Windows build used for Mozilla's June 2022 test is not stated.
- No source tests Windows 11 21H2 on AMD, or separates 23H2 / 24H2 / 25H2.
- Absence of a Windows 10 back-port is "not found", not "proven": no source tested Windows 10 22H2 on Intel with a recent cumulative update.
- Not researched: whether Task Manager "power usage" columns, SRUM or Settings "energy usage" consume EMI data.

## 2. Which in-box driver provides it (intelppm.sys, amdppm.sys, the processor power management (PPM) driver, a PEP)? Is it documented by Microsoft?

### Takeaway
Microsoft does not document a RAPL-backed EMI provider or any driver name for it. One author claim [single-source] says the in-box Microsoft PPM driver does the RAPL-to-EMI bridging on Windows 11; other tools only confirm that no third-party driver or administrator rights are needed. The exact file (intelppm.sys, amdppm.sys or a PEP) is unconfirmed.

### Cited Findings
- Microsoft's EMI page describes only the consumer side: one EMI device interface exists per EMI-compliant metering device, found with SetupDi, GUID {45BD8344-7ED6-49cf-A440-C276C933B053} (also named GUID_DEVICE_ENERGY_METER). It names no in-box provider. — [Microsoft Learn: Energy Meter Interface](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/energy-meter-interface)
- Only source naming a driver [single-source, 2026]: the description of Green Metrics Tool pull request 1801 (author MaximilianJahns) states: "The inbox Microsoft PPM driver on Windows 11 bridges RAPL MSRs to EMI automatically." The same page says no custom kernel driver or test mode is needed, and it contains no device path, no hardware ID, no "intelppm" or "amdppm" string. The page also flags its measurements as author-reported and not independently verified. — [green-metrics-tool PR 1801](https://github.com/green-coding-solutions/green-metrics-tool/pull/1801)
- No specific driver file is required from the user: FOSDEM slide 19 (Mozilla, Feb 2024) says the EMI API is documented, queryable many times per second, usable in user land and needs no specific driver to be installed. — [FOSDEM 2024 slides](https://archive.fosdem.org/2024/events/attachments/fosdem-2024-2716-firefox-power-profiling-a-powerful-visualization-of-web-sustainability/slides/22726/FOSDEM_2024_-_Firefox_Power_Profiling_a_powerfu_Q635bzv.pdf)
- [2026] CodeCarbon says EMI is built into the OS and needs no third-party driver, no administrator rights and no extra dependency; its module says the OS kernel itself exposes the CPU RAPL counters since Windows 11, for Intel and AMD. — [CodeCarbon methodology](https://docs.codecarbon.io/latest/explanation/methodology/), [windows_emi.py](https://raw.githubusercontent.com/mlco2/codecarbon/master/codecarbon/core/windows_emi.py), [codecarbon issue 457](https://github.com/mlco2/codecarbon/issues/457)
- [2026] power-overwhelming says Microsoft provides built-in support for reading the MSRs through EMI from Windows 11 on, and contrasts it with its own driver, which is not WHQL-signed and needs test signing or disabled driver-integrity checks. — [pwrowgrapldrv README](https://raw.githubusercontent.com/UniStuttgart-VISUS/power-overwhelming/master/pwrowgrapldrv/README.md)
- [single-source, 2026] A hobby power monitor (Power-Sentinel) describes the "Energy Meter" counter set as backed by Intel RAPL and AMD SMU hardware counters; no reference is given. — [Power-Sentinel rapl.py](https://raw.githubusercontent.com/oucdc/Power-Sentinel/main/notebook_power_monitor/rapl.py)
- Intel states that the file intelppm.sys is unrelated to the Intel PPM provisioning package and driver that Intel itself ships (Windows 11 24H2/25H2, Core Ultra Series 2 and 3); that Intel article says nothing about energy metering, RAPL or EMI. So Intel's provisioning package is not the EMI provider. — [Intel: PPM Provisioning Package and Driver FAQ](https://www.intel.com/content/www/us/en/support/articles/000100206/processors/processor-utilities-and-programs.html)
- Do not confuse EMI with the older Power Meter Interface (PMI): PMI is a WDM interface with the in-box driver ACPIPMI.SYS for ACPI 4.0 power-metering objects (Windows 7 / Server 2008 R2 on), exposed through WMI classes to PerfMon. That is whole-system power in watts, not the RAPL channels. — [Microsoft Learn: Power Metering and Budgeting overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/overview-of-the-power-metering-and-budgeting-infrastructure)
- Ruled out: Geoff Chappell's page on the HAL "Emon" interface concerns Intel performance-monitoring event counters (MSR 0x186 / 0xC1 family), not energy. — [Geoff Chappell: Emon](https://geoffchappell.com/studies/windows/km/hal/api/hwperfcnt/emon.htm)

### Inferences
- The PPM claim is plausible: (a) channel names carry the prefix RAPL_Package0_ even on a Ryzen 7 5800U, which suggests a Microsoft-authored, vendor-neutral provider and not an Intel- or AMD-branded driver; (b) the channel set differs by vendor (Intel: PKG, PP0, PP1, DRAM; AMD: PKG plus per-core), as the MSRs differ by vendor; (c) nothing has to be installed. Linux's amd_energy documentation says AMD exposes per-core and socket energy through RAPL-style MSRs [snippet-only: https://www.kernel.org/doc/Documentation/hwmon/amd_energy.rst], which matches the per-core AMD channels. If the claim is right, the file would be intelppm.sys on Intel and amdppm.sys on AMD, but this is unverified; a PEP (power engine plug-in) is an alternative nobody has checked.
- The "Energy Meter" PDH counter set already exists on Windows 10 (the caller saw it with zero instances). So the PDH side is old; what Windows 11 adds is the EMI device that feeds it with RAPL data.

### Gaps
- No Microsoft documentation, blog or driver-kit note of a RAPL-backed EMI device or its provider driver.
- No device-interface path or owning device/service name found in any source. To settle it on a Windows 11 box: enumerate device interfaces for the EMI GUID and look at the owning devnode and its service (not done; this research was read-only).
- Intel DPTF / platform-specific providers and AMD's own chipset or PMF drivers as alternative sources of EMI channels were not ruled in or out.

## 3. Which Intel generations are covered (does an 8th-generation Whiskey Lake Core i5-8265U get it on Windows 11)? Are AMD Ryzen processors covered, and with which channel names?

### Takeaway
No coverage list exists from Microsoft, Intel or AMD. Evidence: Intel CPUs on Windows 11 (generation never named) plus Intel Core Ultra 7 255H (Arrow Lake-H) confirmed in October 2026; AMD Ryzen 7 5800U (Zen 3) confirmed on Windows 11 22H2 in October 2022 with PKG and per-core RAPL-style channels. Nothing was found about Whiskey Lake or any other pre-Ice Lake Intel part on Windows 11, positive or negative. Chromium additionally knows four AMD-style channel names (VDDCR_VDD Energy, VDDCR_SOC Energy, Current Socket Energy, Apu Energy) whose origin is undocumented.

- Firefox's Windows code maps RAPL_Package0_PKG to the track label `CPU package`, RAPL_Package0_PP0 to `CPU cores`, RAPL_Package0_PP1 to `iGPU`, RAPL_Package0_DRAM to `DRAM`, and RAPL_Package0_Core%u_CORE to `CPU core N`; any other name is shown as is. It contains no AMD-style names and no Windows build check. — [PowerCounters-win.cpp (gecko-dev mirror)](https://raw.githubusercontent.com/mozilla/gecko-dev/master/tools/profiler/core/PowerCounters-win.cpp)
- Chromium's Windows provider recognises: RAPL_Package0_PKG (package), RAPL_Package0_PP0 (CPU), RAPL_Package0_PP1 (GPU), RAPL_Package0_DRAM (DRAM), and the AMD-style channels `VDDCR_VDD Energy`, `VDDCR_SOC Energy`, `Current Socket Energy`, `Apu Energy`; other names are ignored; there is no PSYS mapping on Windows. Its comments say the metrics are hardware dependent, the RAPL ones come from Intel and the rest from AMD, and only single-socket systems ("Package0") were considered (multi-socket naming is untested). — [energy_metrics_provider_win.cc](https://raw.githubusercontent.com/chromium/chromium/main/components/power_metrics/energy_metrics_provider_win.cc)
- Chromium's shared header says the authors do not know exactly what the four AMD fields measure, that the GPU field is usually the integrated GPU and only on client CPUs, and that DRAM is only available on server CPUs. — [energy_metrics_provider.h](https://raw.githubusercontent.com/chromium/chromium/main/components/power_metrics/energy_metrics_provider.h) A search snippet of Chromium's system_power_monitor.cc shows trace counters named `VDDCR VDD (mW)`, `VDDCR SOC (mW)` and `APU Power (mW)` [snippet-only]. — [system_power_monitor.cc](https://chromium.googlesource.com/chromium/src.git/+/HEAD/components/power_metrics/system_power_monitor.cc)
- Chromium's Windows provider file shows only maintenance commits since its creation on 2023-04-14 (latest commit seen: 2026-02-12; the log page was still loading when read, so older entries could be hidden). The creation commit already adds the shared header with the AMD-specific fields (per the commit page), so the AMD-style channel names had been seen on AMD hardware by April 2023. — [commit log](https://github.com/chromium/chromium/commits/main/components/power_metrics/energy_metrics_provider_win.cc), [Chromium commit 56f5ee5](https://github.com/chromium/chromium/commit/56f5ee5)
- [2026] CodeCarbon claims EMI covers both Intel and AMD on Windows, keeps only package channels (to avoid double-counting per-core subdomains) and has logic for multi-die AMD parts (Threadripper/EPYC) where each die mirrors the same socket-wide counter. — [CodeCarbon methodology](https://docs.codecarbon.io/latest/explanation/methodology/), [windows_emi.py](https://raw.githubusercontent.com/mlco2/codecarbon/master/codecarbon/core/windows_emi.py)
- tasksmack's author states that a machine without an energy-meter driver (AMD or Arm, in his words) simply shows no power column; his test host was Intel only, no AMD or Arm hardware was tested. — [tasksmack PR 2873](https://github.com/mgradwohl/tasksmack/pull/2873)
- A July 2025 Telegraf feature request says Intel package power is covered by an existing plugin but nothing exists for AMD Ryzen on Windows 11; it suggests the Ryzen Master SDK and does not mention EMI (shows EMI was not known there, not that it fails). — [telegraf issue 17341](https://github.com/influxdata/telegraf/issues/17341)

### Inferences
- Intel: RAPL MSRs have existed on Intel client CPUs for many generations, and Windows 11 officially supports 8th-generation Core and newer (general knowledge, not sourced here), so a provider reading those MSRs would plausibly cover Whiskey Lake. There is no direct evidence for the i5-8265U. The quickest test is on that laptop under Windows 11: list the "Energy Meter" counter set instances (or enumerate the EMI GUID) and check for RAPL_Package0_PKG.
- AMD names: two naming families exist. Family A (RAPL_Package0_PKG and per-core RAPL_Package0_CoreN_CORE) was observed on Zen 3 with Windows 11 22H2. Family B (the four VDDCR/socket/APU names) is known only from Chromium's code, where it is already present in the April 2023 creation commit. It is therefore contemporary with Mozilla's family A capture (October 2022), so the two families probably reflect different AMD platforms, OEM/driver stacks or Windows builds rather than a later change; an AMD-supplied EMI source is one possibility. No source ties family B to a CPU generation, Windows build or driver, and Chromium's own header admits it does not know what they measure.
- The Windows DRAM channel is inconsistent across sources (FOSDEM says Intel gives DRAM power; Chromium says DRAM is server-only; GMT saw a DRAM channel stuck at 0). Treat DRAM as "may exist but may read 0 on client CPUs".

### Gaps
- No coverage matrix by CPU generation; nothing on Whiskey Lake, Kaby Lake, Coffee Lake, Comet Lake or Ice Lake on Windows 11.
- No report on AMD Zen 1, Zen 2, Zen 4 or Zen 5 with EMI, and no source for where the four Chromium AMD channel names come from (searches for the strings found nothing outside Chromium; Chromium's issue tracker for bug 1385251 and crbug 40879127 was not reachable).
- Whether the Intel channel set (PP0, PP1, DRAM, PKG) shrinks on newer Intel parts such as Core Ultra is unknown.

## 4. Channel names, units, update rate; virtual machines, Hyper-V / VBS, Arm (Snapdragon)

### Takeaway
EMI reports energy in picowatt-hours with a 100 ns timestamp; one device carries several named channels (V2). The RAPL channels are RAPL_Package0_PKG / _PP0 / _PP1 / _DRAM / _CoreN_CORE; PSYS was not seen on Windows. The hardware counter refreshes about every 2 ms (one author's measurement). Virtual machines are expected to expose nothing (not tested); WSL2 on a Hyper-V-enabled host did not block it (indirect); no data exists for VBS/HVCI and Arm.

### Cited Findings
- Units: AbsoluteEnergy is a running total in the unit given by the device metadata, and the only unit defined for V1 and V2 is picowatt-hours; AbsoluteTime is in 100 ns intervals; the zero point of energy is arbitrary, so clients subtract two samples; power is the energy difference divided by the time difference. — [EMI_CHANNEL_MEASUREMENT_DATA](https://learn.microsoft.com/en-us/windows/win32/api/emi/ns-emi-emi_channel_measurement_data), [EMI_CHANNEL_V2](https://learn.microsoft.com/en-us/windows/win32/api/emi/ns-emi-emi_channel_v2), [Energy Meter Interface](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/energy-meter-interface)
- Client sequence: IOCTL_EMI_GET_VERSION, IOCTL_EMI_GET_METADATA_SIZE, IOCTL_EMI_GET_METADATA, IOCTL_EMI_GET_MEASUREMENT; V2 metadata holds OEM name, model, revision, channel count and a list of channels (unit, name size, UTF-16 name). — [Energy Meter Interface](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/energy-meter-interface), [EMI_METADATA_V2](https://learn.microsoft.com/en-us/windows/win32/api/emi/ns-emi-emi_metadata_v2)
- CodeCarbon's ctypes module gives the IOCTL values 0x224000, 0x224004, 0x224008, 0x22400C, a 16-byte measurement record, and conversion constants 1 pWh = 1e-12 Wh and 1 tick = 1e-7 s; for V1 the single channel name comes from the metadata's hardware name. — [windows_emi.py](https://raw.githubusercontent.com/mlco2/codecarbon/master/codecarbon/core/windows_emi.py)
- Chromium converts with 3.6 nJ per pWh. Firefox accumulates only increasing energy deltas, ignores a sample whose timestamp equals the previous one, treats the timestamp as time since system start in 100 ns units, samples only in the parent process and, for V1, uses the single hardware name as the channel. — [energy_metrics_provider_win.cc](https://raw.githubusercontent.com/chromium/chromium/main/components/power_metrics/energy_metrics_provider_win.cc), [PowerCounters-win.cpp](https://raw.githubusercontent.com/mozilla/gecko-dev/master/tools/profiler/core/PowerCounters-win.cpp)
- Channel semantics (Intel RAPL planes): PKG = whole package, PP0 = cores, PP1 = uncore (usually the iGPU), DRAM. — [Firefox power profiling overview](https://firefox-source-docs.mozilla.org/performance/power_profiling_overview.html) PSYS is not mapped by Firefox or by Chromium's Windows code. — [PowerCounters-win.cpp](https://raw.githubusercontent.com/mozilla/gecko-dev/master/tools/profiler/core/PowerCounters-win.cpp), [energy_metrics_provider_win.cc](https://raw.githubusercontent.com/chromium/chromium/main/components/power_metrics/energy_metrics_provider_win.cc)
- PDH route [single-source]: Power-Sentinel reads `\Energy Meter(RAPL_Package0_PKG)\Power`, states that the counter's CookedValue is in milliwatts (divided by 1000 to get watts), treats a counter stuck at 0 as unavailable and notes the first sample has no elapsed interval (first valid value about one second later). It also reads `\Power Meter(_Total)\Power` / `\Power Meter(Power Meter (0))\Power` as whole-machine counters present on some machines. — [Power-Sentinel rapl.py](https://raw.githubusercontent.com/oucdc/Power-Sentinel/main/notebook_power_monitor/rapl.py), [README](https://github.com/oucdc/Power-Sentinel). The Loment project's issue also names the counter set path `\Energy Meter(*)\Power` for Windows 11 (a feature request, no measurement). — [Loment issue 1296](https://github.com/Loment-Lang/Loment/issues/1296)
- Update rate [2026, single author, not independently verified]: in the Green Metrics Tool pull request the author measured the RAPL hardware value changing about every 2 ms (median 2.00 ms); the EMI helper's practical floor was about 2 ms, GMT's practical minimum sampling interval was 10 ms (5 and 7 ms runs failed its checks), and Windows' default 15.625 ms timer tick matters at 5 ms or less. — [green-metrics-tool PR 1801](https://github.com/green-coding-solutions/green-metrics-tool/pull/1801)
- Update rate, general RAPL [Intel RAPL on any OS]: Mozilla's docs say RAPL values refresh at roughly 1,000 Hz but are probably accurate only at lower rates (about 20 Hz). — [Firefox power profiling overview](https://firefox-source-docs.mozilla.org/performance/power_profiling_overview.html). FOSDEM slide 19 says EMI can be queried many times per second. — [FOSDEM 2024 slides](https://archive.fosdem.org/2024/events/attachments/fosdem-2024-2716-firefox-power-profiling-a-powerful-visualization-of-web-sustainability/slides/22726/FOSDEM_2024_-_Firefox_Power_Profiling_a_powerfu_Q635bzv.pdf)
- Accuracy datapoints [single author]: at 99 ms sampling EMI package energy and the MSR-driver package energy were 84.607 mWh and 84.529 mWh (about 0.1% apart); in a simultaneous run EMI read about 0.7% higher. An earlier run gave 1.81 mWh (14.47 W) for EMI and 1.96 mWh (15.40 W) for the Scaphandre driver; the PR calls this under 1% deviation although the numbers differ by roughly 7-8% (inconsistency in the source). — [green-metrics-tool PR 1801](https://github.com/green-coding-solutions/green-metrics-tool/pull/1801)
- Virtual machines: CodeCarbon documents EMI as working only on Windows 11 on bare metal, with a fallback to CPU-load estimation on VMs; the module has no VM detection and simply fails to find a device. The issue that proposed it describes bare-metal-only operation as an expected limitation, not a tested result. — [CodeCarbon methodology](https://docs.codecarbon.io/latest/explanation/methodology/), [windows_emi.py](https://raw.githubusercontent.com/mlco2/codecarbon/master/codecarbon/core/windows_emi.py), [codecarbon issue 457](https://github.com/mlco2/codecarbon/issues/457). Scaphandre's compatibility table (MSR-driver path, not EMI) says VMs are not yet supported and Arm bare metal is not supported. — [Scaphandre compatibility](https://hubblo-org.github.io/scaphandre-documentation/compatibility.html)
- Hyper-V (indirect): the tasksmack pull request (Oct 2026) shows a `vmmemWSL` process with about 21 W attributed on a Windows 11 host where EMI supplied RAPL_Package0_PKG; WSL2 runs on the Hyper-V platform (general knowledge, not sourced here), so a Hyper-V-enabled host still had a working EMI device. The page does not state the Hyper-V/VBS settings explicitly. — [tasksmack PR 2873](https://github.com/mgradwohl/tasksmack/pull/2873)
- VBS/HVCI: no EMI-specific statement. Related only to third-party MSR drivers: HWiNFO forum threads report Memory Integrity (HVCI) / Core Isolation hiding some sensors and Microsoft's vulnerable-driver blocklist blocking sensor drivers [snippet-only]. — [HWiNFO forum thread](https://www.hwinfo.com/forum/threads/almost-half-of-the-sensors-in-the-cpu-tab-are-missing.8595), [HWiNFO forum thread](https://www.hwinfo.com/forum/threads/memory-integrity-microsoft-vulnerable-driver-blocklist-disables-fan-readings.10259/). The driver-based tools need an unsigned/test-signed driver (power-overwhelming's, Hubblo's `windows-rapl-driver` used by GMT and Scaphandre). — [pwrowgrapldrv README](https://raw.githubusercontent.com/UniStuttgart-VISUS/power-overwhelming/master/pwrowgrapldrv/README.md), [GMT Windows install](https://docs.green-coding.io/docs/installation/installation-windows_native/)
- Arm / Snapdragon: nothing found. Mozilla's slides list no Arm Windows support; CodeCarbon and Chromium name only Intel and AMD channels; tasksmack mentions Arm only as a case where no meter driver exists and the power column is hidden, and did not test Arm. — [FOSDEM 2024 slides](https://archive.fosdem.org/2024/events/attachments/fosdem-2024-2716-firefox-power-profiling-a-powerful-visualization-of-web-sustainability/slides/22726/FOSDEM_2024_-_Firefox_Power_Profiling_a_powerfu_Q635bzv.pdf), [tasksmack PR 2873](https://github.com/mgradwohl/tasksmack/pull/2873)

### Inferences
- Derived from the cited units (my arithmetic): power in watts = 0.036 x (energy difference in pWh) / (timestamp difference in 100 ns ticks); energy in joules = pWh x 3.6e-9. Example: 1,000,000 pWh over 1,000,000 ticks (0.1 s) is 36 mW.
- PKG contains the cores (and, on Intel, the iGPU); summing all channels would double-count. CodeCarbon's package-only rule is the safe pattern.
- Because the hardware value changes every ~2 ms and Windows timers default to ~15.6 ms, polling faster than about 10 ms gives little extra information unless the timer resolution is raised; readings from `\Energy Meter(...)\Power` PDH counters are averages over the PDH sampling interval.
- VM guests: x86 RAPL MSRs are normally not passed to guests, so no EMI RAPL device is the expected result; this is consistent with CodeCarbon but not tested in any source. The Hyper-V root partition (host with WSL2) appears to keep the device. VBS/HVCI should not matter for an in-box driver (they matter for third-party MSR drivers), but no source tests it.
- Arm: RAPL is an x86 mechanism, so Snapdragon PCs would need an OEM/Qualcomm-supplied EMI driver; no evidence one exists for CPU energy.

### Gaps
- No test or Microsoft statement for guest VMs (Hyper-V, VMware, VirtualBox, Azure/AWS, Windows Sandbox), for VBS/HVCI on versus off, or for nested virtualization.
- No data at all for Snapdragon/Arm64 Windows EMI channels.
- Microsoft documents no "Energy Meter" PDH counter set; the milliwatt unit of its Power counter rests on one hobby project (verify on the machine by comparing with EMI-derived watts). Other counters of that set (for example an energy counter) were not confirmed.
- Update rate on AMD is unknown; the 2 ms figure is one author's Intel-class measurement.

## 5. Real-world reports: tools that read it and what they say works or fails

### Takeaway
By late 2026 four independent codebases (Firefox 2022, Chromium 2023, CodeCarbon 2026, tasksmack 2026) plus an open Green Metrics Tool pull request read EMI directly and agree on: Windows 11, bare metal, no driver, package channel RAPL_Package0_PKG as the portable denominator. I found no public report of System Informer, HWiNFO or LibreHardwareMonitor using EMI, and no bug report of missing EMI on specific Intel generations.

### Cited Findings
- Firefox Profiler (Mozilla): implementation enumerates EMI devices through SetupDi, opens each with CreateFile, uses the four IOCTLs, supports V1 and V2, and notes that the symbol GUID_DEVICE_ENERGY_METER does not exist in SDKs older than Windows 10; a 2024 bug proposes simplifying the code because Windows versions below 10 are no longer supported. Landed June 2022, shipped Firefox 104, AMD per-core track naming fixed 2022-10-27. — [PowerCounters-win.cpp](https://raw.githubusercontent.com/mozilla/gecko-dev/master/tools/profiler/core/PowerCounters-win.cpp), [Bugzilla 1873773](https://bugzilla.mozilla.org/show_bug.cgi?id=1873773), [commit list](https://api.github.com/repos/mozilla/gecko-dev/commits?path=tools/profiler/core/PowerCounters-win.cpp&per_page=30)
- Chromium (power_metrics): EMI provider since April 2023; takes the first EMI device interface it finds, with an open TODO whether the first is always the right one (crbug 40879127); reports package, CPU, GPU, DRAM and the four AMD fields in nanojoules; single-socket assumption. [older for design, active in 2026 per commit log] — [energy_metrics_provider_win.cc](https://raw.githubusercontent.com/chromium/chromium/main/components/power_metrics/energy_metrics_provider_win.cc), [Chromium commit 56f5ee5](https://github.com/chromium/chromium/commit/56f5ee5). An older Chromium tool (tools/win/IdleWakeups power sampler) still depends on Intel Power Gadget's EnergyLib64.dll, i.e. pre-EMI [snippet-only]. — [power_sampler.cpp](https://chromium.googlesource.com/chromium/src/+/201e747d032611c5f2785cae06e894cf85be7f8a/tools/win/IdleWakeups/power_sampler.cpp)
- CodeCarbon (2026): backend `windows_emi` chosen when an EMI device is readable; fallbacks are Intel Power Gadget if installed, then CPU-load estimation, then a constant. Keeps only package channels; DRAM only if an option is set; no admin rights or third-party driver. Issue 457 (Intel Power Gadget being deprecated) was the trigger; the EMI proposal is dated 2026-07-05 and the issue was closed 2026-08-03. The EMI code path lives in the separate windows_emi module; the current cpu.py module only contains the Intel Power Gadget route on Windows. — [CodeCarbon methodology](https://docs.codecarbon.io/latest/explanation/methodology/), [windows_emi.py](https://raw.githubusercontent.com/mlco2/codecarbon/master/codecarbon/core/windows_emi.py), [cpu.py](https://raw.githubusercontent.com/mlco2/codecarbon/master/codecarbon/core/cpu.py), [issue 457](https://github.com/mlco2/codecarbon/issues/457)
- Green Metrics Tool (GMT): current Windows-native docs list a single CPU provider, `cpu_energy_rapl_scaphandre_component`, which needs Hubblo's windows-rapl-driver (test-signing mode, driver started before each run, device `\\.\ScaphandreDriver`), default 99 ms, domains cpu_package, cpu_cores, cpu_gpu, dram, psys. — [GMT Windows install](https://docs.green-coding.io/docs/installation/installation-windows_native/). A separate pull request adds `cpu_energy_rapl_emi_component` (no custom driver, no test mode; DRAM channel present but 0 on the test system; results above). As of the last fetched comments (dated Nov 9; the year is not shown in the fetched text but fits 2026) the PR was still under review with requested changes and CodeRabbit findings (wrong installer paths, unchecked exit code, EMI warnings flooding a pipe); no merged docs page existed (the expected docs URL returned 404). — [green-metrics-tool PR 1801](https://github.com/green-coding-solutions/green-metrics-tool/pull/1801), [expected docs page (404)](https://docs.green-coding.io/docs/measuring/metric-providers/cpu-energy-rapl-emi-component)
- Scaphandre / Hubblo windows-rapl-driver: Windows support goes through the MsrRAPL sensor plus the driver reading RAPL MSRs; its compatibility table says Intel bare metal yes, AMD probable yes (not tested), Arm no, VM not yet; no mention of EMI. — [Scaphandre compatibility](https://hubblo-org.github.io/scaphandre-documentation/compatibility.html)
- power-overwhelming: `emi_sensor` is the recommended route on Windows 11; `msr_sensor` needs the project's own driver that is not WHQL-signed and needs test signing or disabled integrity checks and weakens security. — [pwrowgrapldrv README](https://raw.githubusercontent.com/UniStuttgart-VISUS/power-overwhelming/master/pwrowgrapldrv/README.md)
- tasksmack (Windows task-manager clone, Oct 2026): per-process power by sharing the EMI package energy by CPU time (issue found 2026-10-19, closed 2026-10-24); finds the device via SetupAPI on a worker thread because enumeration can stall on a slow ACPI call; hides the feature when no EMI device exists; had to exclude the System Idle Process from the share (it showed 8.2 W for "[System Process]" before the fix); tested on Intel Core Ultra 7 255H. — [tasksmack PR 2873](https://github.com/mgradwohl/tasksmack/pull/2873), [issue 2587](https://github.com/mgradwohl/tasksmack/issues/2587)
- Power-Sentinel (notebook tray app): reads the PDH counter `\Energy Meter(RAPL_Package0_PKG)\Power`, shows an unavailable state with a reason when the counter is missing or 0; lists Windows 10/11 as the run requirement but says nothing about Intel versus AMD. — [Power-Sentinel README](https://github.com/oucdc/Power-Sentinel), [rapl.py](https://raw.githubusercontent.com/oucdc/Power-Sentinel/main/notebook_power_monitor/rapl.py)
- Loment (Loment-Lang/Loment, a language/toolchain project by the look of the issue text): issue 1296 (titled as a missing energy-meter/RAPL path on Windows; severity label sev-5, described there as silently wrong results) asks to implement the Windows 11 PDH counter set `\Energy Meter(*)\Power` first, because the MSR path needs a signed driver and administrator rights; it is an open request and contains no measurement. — [Loment issue 1296](https://github.com/Loment-Lang/Loment/issues/1296)
- Negative findings: I found no evidence that System Informer, HWiNFO or LibreHardwareMonitor read EMI (the HWiNFO forum snippets in section 4 show its sensors being blocked by HVCI and driver blocklists, which suggests it relies on its own kernel-level access rather than EMI; this is my inference). A DEV Community article on reading CPU power registers on Windows never mentions EMI and says a kernel driver is needed (it also reports antivirus false alarms for such drivers). — [DEV article](https://dev.to/daminoup88/reading-cpu-power-registers-on-windows-almost-broke-me-heres-what-i-learned-building-a-power-4iel)

### Inferences
- EMI has become the default driverless route on Windows 11 in 2026 (CodeCarbon default, GMT in review, power-overwhelming recommendation); driver-based RAPL (Scaphandre, Hubblo, power-overwhelming driver) is the fallback for Windows 10 and for machines without an EMI device.
- Only the package channel is common to all adopters; per-core and PP0/PP1/DRAM channels are CPU- and OS-dependent, so a tool should discover channels by name and treat PKG as the primary value.
- Practical failure modes reported or implied: no EMI device (Windows 10, VMs, some hardware), device enumeration latency, DRAM reading 0, counter stuck at 0 in PDH, multi-socket and multi-die systems (double counting), and sampling jitter below 10 ms.

### Gaps
- No evidence about System Informer, HWiNFO or LibreHardwareMonitor usage of EMI; searched by name, nothing found.
- No independent reproduction of the GMT accuracy figures; all numbers come from the PR author.
- No bug report found on missing EMI for a named Intel generation; the search tool's coverage of forums and trackers is limited, so absence is weak evidence.
- Firefox's current repository path may have moved from the gecko-dev mirror used here; the mirror's file could be stale relative to Firefox 14x/15x (its latest commit touching the file was January 2025).
